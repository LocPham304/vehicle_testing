# Wi-Fi HTTP implementation plan

Approved scope: add a separate direct HTTP control mode in vehicle_testing.
No MQTT broker, USB cable, FE/BE edits, access-point setup or firmware migration.
Laptop and Pi must be reachable on the same IP network. Default TCP port 8765.

Architecture: wifi_receiver.py uses a ThreadingHTTPServer with bounded JSON
requests and the existing RobotSession/parser/runner. wifi_client.py uses urllib
and the same interactive command console as USB. Both use Python standard library.
Preview is default; --dry-run executes simulated outputs; --run enables hardware.

Interface: POST /connect returns a temporary session token; control requests carry
X-Session-Token. POST /upload, /run, /stop, /ping, /disconnect; GET /status and
/events?after=N. Source is JSON {id,code}, never evaluated. IDs use existing bounded
deduplication. A single controller lease prevents simultaneous laptop control;
valid heartbeat renews it, 5-second expiry stops/reset the session. A watchdog
continues independently of the HTTP request threads. Bounded sequenced events
preserve execution/block reports until polled. No wildcard browser CORS.

Files: wifi_receiver.py, wifi_client.py, control_console.py;
script_session.py neutral log wording; usb_client.py reexports shared console;
tests/test_wifi.py, tests/test_wifi_client.py, docs/WIFI.md, README.md.

Steps:
- Write failing tests for upload-only, exact uploaded source, busy/stop, owner,
  token expiry, stale/duplicate requests, malformed/oversized HTTP, event polling.
- Implement receiver and watchdog, preserving all existing USB/MQTT behavior.
- Extract the unchanged USB console and add HTTP client with automatic ping/events.
- Exercise direct HTTP on loopback with real client, simulated runner, and network
  loss. Run relevant USB/MQTT/parser/runner regressions.
- Document laptop versus SSH commands, no-broker test and hardware mode.

Limits: lab/LAN prototype; no Internet hosting, TLS/user authentication or web FE
integration. Token represents temporary controller ownership, not account login.
Process/I2C failure can still prevent a software stop; no hardware stop guarantee.

Implemented and verified on Windows: 94 related tests passed, including the three
opt-in real HTTP loopback tests. Coverage includes separate upload/run, Unicode,
busy/deduplication, controller lease, independent expiry cancellation, bounded
events, HTTP validation, and existing USB/MQTT/parser/runner behavior. Direct CLI
help loads without GPIO/serial dependencies. No physical Pi/Wi-Fi test performed.
