# Wi-Fi UDP receiver implementation plan

## Confirmed contract and design

The user's live Pi capture establishes the external BE contract, superseding
the earlier Java example: one datagram is `UUID\nUTF-8 source`; execute is
exactly `UUID\nEXEC`. For robot-003 the EXEC datagram is 14 bytes. Receive on
IPv4 wildcard UDP port 50000. Keep the HTTP receiver and all other transports.

Implement an additive adapter in `connections/wifi/udp_receiver.py`, with root
launcher `wifi_udp_receiver.py`. Reuse RobotSession and execute_program; never
evaluate received source. Default preview; explicit --dry-run or --run.
Require --device-id; allow --sender-ip to restrict the BE IPv4 address.
Ignore other UUIDs before decoding source. Invalid own uploads invalidate the
pending program. A successful upload arms one EXEC; consume it on accepted
execution, so duplicate EXEC packets cannot repeat completed movement. A new
upload is required for another run. Reject uploads during an active run.
On shutdown cancel/join the worker. Socket receive loop stays responsive while
the session runs on its existing worker.

No response, discovery, STOP command, heartbeat, message ID or fragmentation
metadata has been supplied by BE. Do not invent these fields or packets.
Only support a complete script in one datagram; documentation must state that
the current wire format cannot detect missing/reordered script chunks, stale
EXEC packets, or a duplicated complete upload/EXEC pair. No exactly-once claim.
No automatic network-loss stop without a supplied heartbeat contract.

## Results

Observed missing-module assertion fail before implementation. All 14 UDP tests
passed with real loopback enabled outside the network-restricted sandbox.
The sandbox run could bind but did not deliver the loopback upload; the same
test passed with local network access. The full suite with HTTP, UDP and BT
stream integrations enabled passed: 321 tests in 42.596 seconds. Startup/help
works outside the repo. Read-only independent review found no actionable issues.
No physical Pi/motor or external BE execution was performed by these tests.

## Validation boundaries

All local tests use fake executors or the dry-run runner. No GPIO or motors.
The user must update the Pi checkout and test the external FE/BE buttons.
Student discovery and global control ownership across transports are outside
this adapter; targeted delivery is by configured UUID only.
